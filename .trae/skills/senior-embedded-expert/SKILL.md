## 核心能力

### 1. 深度Bug排查方法论

**排查流程（强制执行）**：
```
1. 收集证据 → 2. 提出假设 → 3. 交叉验证 → 4. 定位根因 → 5. 修复验证
```

**日志分析技巧**：
- 对比正常日志和异常日志的差异
- 关注时间戳和执行顺序
- 注意日志级别和过滤条件

**代码审查技巧**：
- 检查变量作用域和生命周期
- 对比Master和Slave的协议约定
- 验证枚举值和实际值的映射关系

**交叉验证技巧**：
- 确认修改影响范围（相关文件是否需要同步修改）
- 使用对比实验（改一处vs改多处）

### 2. 枚举状态架构

**核心原则**：所有设备状态必须使用枚举类型，禁止使用裸 `uint8_t`。

```c
/* 错误示例 - 裸uint8_t */
uint8_t servo_angle = 90;  // 含义不清

/* 正确示例 - 枚举类型 */
typedef enum {
    SERVO_0   = 0,
    SERVO_45  = 1,
    SERVO_90  = 2,
    SERVO_135 = 3,
    SERVO_180 = 4
} servo_angle_enum_t;

servo_angle_enum_t servo_angle = SERVO_90;  // 含义清晰
```

**枚举 → 实际值映射表**：
```c
static const int16_t g_servo_angle_map[5] = {
    [SERVO_0]   = 0,
    [SERVO_45]  = 45,
    [SERVO_90]  = 90,
    [SERVO_135] = 135,
    [SERVO_180] = 180
};

// 使用时：实际角度 = g_servo_angle_map[枚举值]
```

### 3. 条件编译模式设计

**DEBUG_MODE 设计原则**：
- `#define DEBUG_MODE 0` = 正常模式（小智/远程控制）
- `#define DEBUG_MODE 1` = 调试模式（本地按键控制）

```c
// 条件编译示例
#if DEBUG_MODE == 1
    // 按键初始化和轮询
    HW_Button_Init(DEBUG_BTN_GPIO);
    if (HW_Button_Is_Pressed()) {
        Debug_Servo_Step();
    }
#else
    // ESP-NOW 舵机刷新
    HW_Servo_Set_Angle(g_servo_channels[i], g_servo_angle_map[g_device_flags.servo[i]]);
#endif
```

### 4. 协议层Index映射

**Master-Slave通信核心原则**：
- Master发送的是**全局GPIO索引**（如6,7,8）
- Slave需要根据本地设备布局进行**索引转换**

```c
/* Master发送：gpio_index=6 (全局索引) */
/* Slave接收后需要转换 */
uint8_t local_index = gpio_index - 6;  // 转为本地索引0,1,2
g_device_flags.servo[local_index] = ...;
```

### 5. 分层注释规范

```c
/* ================= 1. 硬件底层函数 (HW_ 前缀) ================= */
static void HW_Gpio_Write(gpio_num_t gpio, uint8_t level) { ... }

/* ================= 2. 业务逻辑变量 ================= */
static uint8_t g_device_state = 0;

/* ================= 3. 对外功能入口 ================= */
void Device_Control_Set_State(uint8_t state) { ... }
```

## 排错经验库

### Bug类型1：枚举值vs实际值混淆

**症状**：日志显示命令执行了，但设备行为异常

**典型案例**：
- `all_on` 设置 `servo = SERVO_90`（枚举值=2）
- `set_servo_by_index` 设置 `servo = 90`（实际角度值）
- 两者都执行了，但后者使用 `g_servo_angle_map[90]` = 越界访问！

**排查方法**：
1. 对比两个控制路径的日志
2. 打印枚举值和实际值
3. 检查映射表访问是否越界

### Bug类型2：Index映射错误

**症状**：命令被接收但设备不响应

**典型案例**：
- Master发送 `gpio_index=6,7,8`
- Slave检查 `gpio_index < 3`（错误！应该是 >=6）
- 命令被验证逻辑拒绝

**排查方法**：
1. 确认Master和Slave的协议约定
2. 打印接收到的原始gpio_index
3. 验证范围检查逻辑

### Bug类型3：条件编译路径覆盖

**症状**：某模式下设备不响应，但代码看起来没问题

**典型案例**：
- DEBUG_MODE==1 时ESP-NOW路径被注释掉
- 按键调试正常，但小智控制失败

**排查方法**：
1. 确认DEBUG_MODE当前值
2. 检查条件编译分支是否正确
3. 使用 `#if DEBUG_MODE == X` 而非 `#ifdef`

## 交互指南

### 1. 询问澄清（必要步骤）

遇到以下情况时，**必须先问清楚再做修改**：
- 用户需求描述模糊时
- 不确定DEBUG_MODE应该影响哪些功能时
- 不确定两个控制路径是否可以共存时

**询问模板**：
> "我理解你想要XX功能，但请确认：
> 1. DEBUG_MODE==1时，按键和小智是否需要同时控制舵机？
> 2. 还是DEBUG_MODE==1时只有按键，DEBUG_MODE==0时只有小智？"

### 2. 验证假设

修改前必须验证：
- [ ] 影响范围：需要修改几个文件？
- [ ] 相关性：类似代码是否需要同步修改？
- [ ] 可逆性：修改是否容易回退？

### 3. 精准描述

给出修复时必须包含：
- **根本原因**：不只是"不工作"，要解释"为什么不工作"
- **修改位置**：具体文件和行号
- **修改内容**：修复前vs修复后代码对比

### 4. 进度可视化

使用TodoList让用户了解进度：
```
[进行中] 深度分析问题根因
[待处理] 修复Firstfloor代码
[待处理] 修复Secondfloor代码
[待处理] 验证测试
```
